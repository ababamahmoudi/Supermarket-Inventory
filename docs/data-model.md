# Data model

Current contracts include C6/C7 (2026-10-11). Earlier C3/C4/C5 compatibility notes are historical where superseded by the C6 section below.

Database: PostgreSQL. This document defines entities and rules, not exact column types; the AI developer finalizes migrations and records changes here.

## Conventions

- Primary keys: UUID. Every table has `created_at`, `updated_at`, `created_by` where a person acts.
- Every business table has `company_id`; branch-level tables also have `branch_id`. Enforce scoping in a shared base query layer and test it.
- Money: `Decimal(12,2)` for selling prices, invoice totals, ledger amounts; `Decimal(12,4)` for unit costs.
- No hard deletes. Use status/archived flags or void with a reason.
- Free text and names support `*_en` and `*_fa` columns (or a translations table). Custom notebooks require English and allow Persian to be empty, with an English display fallback; preserve both fields rather than manufacturing a translation.
- Use an append-only `audit_log` for sensitive actions.

## Seed loading

`seed/arzon-config.json` is loaded by an idempotent management command: it creates the company, branches, roles' labels, pricing categories, bands, offer definitions, settings, and terminology. It must be safe to run repeatedly, and C authorizes idempotent company-scoped built-in Regular/Promo templates in the prototype. Existing saved/archived template edits are preserved; inserting built-ins does not reset geometry or recreate an archived template. The separately maintained backend seed command is outside the C prototype change scope.

**Correction finance:** paired adjustments move only the invoice's current outstanding liability. Existing source payments/credits and allocations remain immutable; source outstanding closes and destination outstanding is projected from the correction. Preserve company/supplier/currency total and evidence. Future shorts/corrections resolve effective destination. Previously approved selling prices are not reapplied merely because an invoice location moved.

**Quantities and money:** all cost/expected/payable arithmetic uses Decimal; Each Units are positive whole; Weight quantities are positive kg/lb values with at most three decimals and retain source quantity/cost units; cases use exact Decimal positive quantity × positive integer pack and must normalize to positive whole units, with no float scaling/rounding. A fractional case is allowed only if this condition holds. Snapshot pack/cost on posted invoice/order so later supplier-item edits never alter history. Short-dated lots retain actual low-cost receipts/payable and Date tracking, but do not replace regular cost or create selling-price proposals.

**Receipt identity and corrections:** price comparisons use the accepted purchase history for the same supplier identity and supplier item, including supplier rename aliases; fully refused lines and another SKU are not price evidence. Uploaded and manual invoice lines remember a uniquely matched supplier item's pack without changing the original quantity or cost; ambiguous matches require review. Later Short deliveries identify the original invoice line, so two supplier codes for one product remain separate. Each order receipt retains its actual `receiving_branch`. After a posted invoice is moved, later delivery is authorized at its corrected location and History records that location, while original invoice/order locations and pack/cost snapshots remain unchanged.

## C6 persistence representation — not new business entities

- **File evidence:** `StoredFileRecord` retains company/reference, original name/type/size, SHA256, immutable source Blob, preview Blob/dimensions and saved UTC time. Source bytes remain exact; image derivatives have longest side ≤2000 px. File refs never point to ephemeral object URLs. Reads validate same-company identity and source hash/size.
- **Raw recovery snapshot:** `FileBackupRecord` retains company, source storage key, raw JSON Blob, SHA256 and saved time; `idb-backup:v1:<encoded-company>:<encoded-storage-key>:<SHA256>` identifies it. Verify raw text and hash after committed write before replacing any inline source/old migration backup/main C6 state. Preserve exact original raw strings, not merely a transformed backup. Failed/interrupted migration or stale source never republishes old business values or drops retained evidence.
- **History storage dictionary:** the private persisted `prototype_history_dictionary` has version 1, typed blocks, permitted binding paths and an integrity checksum. It may replace only large repeated activity before/after/reversal/transfer/guard values with bound reference placeholders, retaining all entries and metadata. Decode/validate before reading state for domain logic. The in-memory/API-domain shape and meaning remain unchanged; no new business table or permission field is implied. Store the dictionary only when smaller than ordinary JSON.
- **Integrity boundary:** dictionary checksum is accidental-corruption detection, not cryptographic authentication. Validate exact schema, finite values, unique bindings/keys, allowed paths and non-cyclic bounded references. Malformed persisted dictionary retains the raw original and blocks automatic write-back; never silently replace it with seeded business records. Source file/raw backup SHA256 checks remain separate cryptographic content-integrity checks.
- **No deletion:** replacing file/History representation is not Undo, a physical/financial movement or an audit action. Resetting fictional business state does not automatically delete immutable files/raw backups. Exact originals, company scope, original ordering, reversible snapshots and current financial allocations survive round-trip.

Automated final proof must demonstrate codec equality/corruption rejection plus twenty real photos, exact downloads, reload and nearly-full legacy text-storage migration; actual results belong in the C6 review guide after execution.

### API contract for the browser domain and future server

Use `SalesContext` (company, actor/capabilities, allowed locations and supplied UTC clock) and `ChangePriceInput` (product, mode, exact price/unit, reviewed target stores, dates, label choice, acknowledgement/reason and expected revision). Keep pure preview/validation separate from guarded state changes.

Canonical names: `regularPrice`, `activeSaleAt`, `previewPriceChange`, `validatePriceChange`, `savePriceChange`, `changeSale`, `endSale`, `syncSales`, `requestSale`, `editSaleRequest`, `withdrawSaleRequest`, `resolveSaleRequest`, `recordSaleReceiptCost`, `decideSaleCostAlert`. Existing History Revert consumes sale-specific versioned inverse evidence. Mutations validate company, permission, concrete selling scope and stale revisions atomically; failure writes none.

`manualRegularApprovalPreview(state, approval, decision = "rule")` is the pure preview for the two regular-price choices. It exposes the selected price, retained regular/calculated prices, actual received-cost margin/threshold, below-minimum/below-cost flags and whether the retained manual price can still be kept. `resolveApproval` retains its existing arguments and adds an optional final `regularDecision: "rule" | "keep"`, defaulting to `"rule"`. Recheck the actual company, pending approval, receiving store, retained price/manual provenance, current cost and expected snapshot before applying a decision. Keep is restricted to that original store and preserves provenance. For either Rule or Keep, require a reason when the selected price is below the configured minimum margin or below cost. Missing-reason copy is **Add a reason.** / **یک دلیل اضافه کنید.** The receiving recommendation never authorises or suppresses the final approval. Record the final decision without altering immutable receipt evidence.

A sale alert retains its original `approval_id` and before/after snapshots. Its display resolves the actual linked approval status: pending uses the pending proposal and waiting caption; absent/decided uses the current regular price. Presentation does not rewrite the alert's source values.

`regularPrice` is the existing approved baseline. Effective selling-price projection returns regular provenance, active sale price/unit/dates, safe pending request, ordinary multi-buy paused state and independent lot clearance. Invoice comparisons always use regular cost/price, not the sale overlay. Targets snapshot the currently eligible stores actually reviewed. Warehouse and non-selling/inactive locations are excluded.

Weighed sales retain exact entered main-unit cents. Normalize to a common unit with full Decimal precision for comparisons/margins; derive secondary display with existing cent rounding. Do not rewrite the canonical regular price merely because main display changes. Currency text is min 2/max 4 decimals; stored costs/ledger allocation are unchanged. Each case display divides exact normalized units by the retained pack into whole cases and a loose-unit remainder, without changing source quantities.

`syncSales(state, context)` uses the supplied UTC clock and each store's IANA zone (company fallback). Local start dates and midnight after inclusive last day define intervals; do not use UTC day slices or 24-hour duration arithmetic. Lifecycle effects are idempotent. A Revert reevaluates current time and version guards; it cannot revive an elapsed schedule or restore an unrelated regular-price snapshot.

Open product dates are active/unremoved, including past dates. Saving with tracking Yes queries for an open date anywhere in the company without returning unauthorized other-store facts. A staged inline date is included in the same validated product save.

The four canonical Alert types are `sale_cost_increase`, `sale_regular_not_above_sale`, `sale_no_end_reminder` and `sale_delivery_release`. Public copy remains the owner's exact wording. Each alert/reminder has a scoped source identity and retained decision/read state. New regular-price automatic labels are deferred until actual sale end; the existing Promo queue intent is preserved, and the dialog summary explains when Regular labels will be added.
